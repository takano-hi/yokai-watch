# /implement

入力: $ARGUMENTS

以下を順に実行する。各フェーズの開始時に 1 行で進捗を伝える。

## 1. 要件の取得

- 数字だけなら Issue 番号として `gh issue view <番号>` で本文を取得する（gh が使えなければユーザーに本文を求める）
- 受け入れ条件が読み取れない場合、ここでだけ質問してよい。以降は人に確認せず最後まで進める

## 2. 計画

`planner` サブエージェントに要件を渡す。計画が複数ファイル・新機能なら `docs/<topic>.md` に保存する。

## 3. ブランチ

未コミットの変更があれば、それを含めて良いかをユーザーに確認する。
`git switch -c feat/<短い英語のトピック>`（Issue なら `feat/<番号>-<トピック>`）。

## 4. 実装

- API 変更がある場合: まず `api-dev` に計画の該当部分を渡す。完了報告のリクエスト/レスポンス形を受け取る
- Web 変更がある場合: `web-dev` に計画の該当部分と api-dev の報告を渡す
- api と web が独立している（契約変更がない）なら並行して起動してよい

## 5. 検証

`bash .claude/hooks/quality-gate.sh` を実行する。失敗したら該当のサブエージェントに失敗出力を渡して修正させる。**最大 3 回**。それでも失敗する場合は中断して状況を報告する。

## 6. レビュー

`reviewer` に差分レビューを依頼する。「必須」の指摘は担当サブエージェントで修正し、5 に戻る（レビュー→修正も最大 2 周）。「推奨」以下は報告に含めるだけでよい。

## 7. コミットと報告

- 目的ごとに分けてコミットする（例: API とテスト / Web）。push はしない
- 最後に日本語で報告する:
  - 何を実装したか（ユーザー視点で 2〜3 行）
  - 変更ファイル
  - 検証結果（実行したコマンドと結果）
  - 未対応のレビュー指摘、人の目視確認が必要な点
  - 次の操作の提案（例: `git push -u origin <branch>` して PR 作成）
